### 여기서 반드시 남길 실험

`docs/evaluation.md` 에 표로 정리하세요. 이력서 숫자를 이 표에서 가져옵니다.

| factors | alpha | log_scaling | Recall@10 | NDCG@10 | Coverage@10 |
|---|---|---|---|---|---|
| 16 | 40 | O | | | |
| 32 | 40 | O | | | |
| 64 | 40 | O | | | |
| 128 | 40 | O | | | |
| 64 | 1 | O | | | |
| 64 | 40 | X | | | |
| — 인기순 기준선 — | | | | | |

인기순 기준선을 꼭 같이 넣으세요. "ALS 가 인기순보다 Recall 이 X%p 높다" 가
없으면 나머지 숫자가 의미를 갖지 못합니다.

`factors` 를 키우면 Recall 은 오르는데 Coverage 는 떨어지는 지점이 보통
나옵니다. 그 지점을 찾아서 문서에 적으면 그게 곧 면접 답변입니다.

### 미리 알려드리는 함정: ALS 가 인기순보다 못 나올 수 있습니다

이 설정으로 먼저 돌려봤을 때 실제로 나온 값입니다 (유저 800명 / 45일).

| 모델 | Recall@5 | NDCG@5 | Coverage@5 |
|---|---|---|---|
| 인기순 기준선 | 0.474 | 0.321 | 0.20 |
| ALS (factors=64, α=40, log) | 0.323 | 0.176 | **1.00** |

당황하지 마세요. 버그가 아니라 **데이터와 지표의 성질**입니다. 원인이 셋 있습니다.

1. **카탈로그가 25개뿐입니다.** Recall@10 은 25개 중 10개를 찍는 것이라
   무작위로도 40%가 나옵니다. 이 규모에서는 **K=3~5로 평가**해야 변별력이 생깁니다.
2. **정답이 인기 위젯일 확률이 높습니다.** 홀드아웃한 마지막 클릭 1건은
   생성 과정상 상당수가 전역 인기 위젯입니다. 인기순은 그걸 그냥 맞힙니다.
3. **min-max 정규화가 인기도 정보를 날립니다.** ALS 점수의 절대 크기에 담겨
   있던 "이건 원래 다들 많이 쓴다" 가 유저별 정규화로 지워집니다.

이걸 그냥 적으면 감점이지만, **원인을 짚고 대응을 붙이면 가점입니다.**
써볼 만한 대응:

- 평가 K 를 5로 낮추고, 그 근거(카탈로그 크기)를 명시
- `personas.yaml` 의 `persona_ratio` 를 올려 개인화 신호를 키우기
  → 개인화가 강한 데이터일수록 ALS 우위가 드러납니다
- α와 `log_scaling` 조합 재탐색 (α가 너무 크면 헤비 유저에 과적합)
- ALS 점수에 인기도 사전확률을 소량 섞은 하이브리드로 비교

그리고 Coverage 1.00 vs 0.20 은 그 자체로 강력한 결과입니다.
"인기순은 25개 중 5개만 평생 노출하고, ALS 는 25개를 전부 노출한다."
Recall 이 조금 낮아도 **롱테일 기능의 발견 가능성**을 샀다는 이야기가 됩니다.
이 트레이드오프를 설명할 수 있으면 지표 하나 이기는 것보다 훨씬 좋은 답변입니다.

**커밋**: `feat: Implicit ALS 모델 학습 및 오프라인 평가`

| 함수 | 핵심 |
|---|---|
| `build_user_states` | groupby 한 번으로 유저 상태 생성 (for 문 금지) |

uvicorn src.api.main:app --reload

curl -i "http://localhost:8000/recommend/u000001?now=2025-10-15T10:30:00"
curl -i "http://localhost:8000/recommend/u000001?now=2025-10-25T10:00:00"
